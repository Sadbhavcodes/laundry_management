LaundryHub — Implementation Plan
Oct 20, 2026
This document is the build plan for LaundryHub, the web-based laundry management
system specified across Lab Assignments 1–7 (Team T046, Course CS314, LNMIIT). It
translates the SRS, UML models, and Assignment 7 interface/pseudocode design into an
actual deployable application, phase by phase. Every phase below maps back to specific
FR/BR/UC numbers from the source document so the implementation stays traceable and
defensible in a viva or technical interview. Each phase ends with a ready-to-use prompt
that can be handed to an AI coding assistant (or used as a personal checklist) to execute
that phase consistently with the design.
Request flow: React + TypeScript + Vite (hosted on Vercel) → Supabase Edge
Functions (Deno/TS) implementing IOrderService, IScheduling, IDelivery,
IInvoiceService, INotification → Postgres (Supabase) with RLS policies and
transactional functions for atomic invariants → external SMS/Email provider, called from
an Edge Function acting as the NotificationGateway boundary class.
This mirrors the layered client–server architecture mandated in Section 47 of the SRS: a
presentation layer, an application-service layer coordinating the domain model, and a
persistence layer — except here the persistence layer also carries some of the invariant
enforcement (via Postgres functions and RLS), giving defense-in-depth: even if a bug
slipped into the Edge Function layer, the database would still refuse a role violation or a
partial slot reservation.

Critical Invariants Checklist
These must hold regardless of which phase touched the code last — re-verify them
whenever a later phase edits a function from an earlier one:
1. BR-002 — an Order cannot be submitted without at least one OrderItem.
2. BR-003 — both pickup and delivery slots reserve atomically; a failed reservation never
leaves exactly one slot booked.
3. OrderStatus retains exactly the 8 documented values (Created, Pickup Scheduled,
Picked Up, In Processing, Ready, Out for Delivery, Delivered, Cancelled) — no ad-hoc
extra states.
4. BR-007 — Delivered is reachable only when every cataloged item has an explicit
handover confirmation or exception outcome.
5. Missing or damaged items create a DeliveryException and set Order.reviewFlag =
true instead of silently completing delivery.
6. BR-006 — an Invoice is generated only after a successful transition to Delivered, and
generation is idempotent (at most one invoice per order, safe to retry).LaundryHub — Implementation Plan
